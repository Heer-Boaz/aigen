# Image-edit prompting contract

This document is required reading before writing, rewriting, reviewing, or
approving an image-generation or image-editing prompt in this repository. It
applies to FLUX.2 Klein and Qwen-Image-Edit, including prompts used to create
reverse-source images for a paired pix2pix corpus.

The core rule is simple:

> Write a normal, direct visual instruction. Do not narrate model reasoning,
> invent object relationships, or fight ambiguity with a wall of constraints.

## Primary references

These rules are derived from model-owner documentation and reference code, not
from generic prompt folklore:

- Black Forest Labs' [FLUX.2 prompting
  guide](https://docs.bfl.ai/guides/prompting_guide_flux2) for `[pro]` and
  `[max]` recommends natural language in the order
  `subject + action + style + context`, puts the most important information
  first, and describes 10–30 words as short and 30–80 words as the usual
  medium range. This repository adopts that shared-family structure for Klein;
  it is policy informed by the guide, not a claim that the page documents
  Klein-specific sampling behavior.
- Black Forest Labs' [single-reference editing
  guide](https://docs.bfl.ai/guides/prompting_editing_single_reference) uses
  direct instructions such as “Change it to Night”, “Turn the image into an oil
  painting with thick, textured brushstrokes”, and “Change the shirt color to
  red”.
- Black Forest Labs' pinned
  [FLUX.2 Klein Space prompt
  rewriter](https://huggingface.co/spaces/black-forest-labs/FLUX.2-klein-9B/blob/5f2efb702b95573c788fef63dc17ec2833d64887/app.py#L131-L158)
  asks for one concise instruction, about 30 words for a brief request and
  50–80 for a more involved one. It says to name actual image elements, state
  the change and necessary preservation, use clear language, and turn
  avoidant wording into positive wording. This is an optional external VLM
  wrapper around a Klein demo, not evidence about the 9B checkpoint's sampling
  behavior.
- Black Forest Labs' [FLUX.2
  overview](https://docs.bfl.ai/flux_2/flux2_overview) says Klein has no built-in
  prompt upsampler and recommends detailed, descriptive prompts. “Detailed”
  means sufficiently concrete for the requested edit; it does not require
  diagnostic or repetitive prose.
- Qwen's pinned
  [`polish_edit_prompt`
  implementation](https://github.com/QwenLM/Qwen-Image/blob/6b5e1f5cec987d404be5ac6657db3b9aacb56a89/src/examples/tools/prompt_utils.py#L177-L258)
  asks for a “direct and specific” prompt. If the original instruction is
  already clear, it preserves the intent and only refines its grammar. It adds
  only minimal sufficient detail and uses concise key visual traits for style
  conversion.
- Qwen's [official repository](https://github.com/QwenLM/Qwen-Image) uses
  ordinary edit instructions such as “make the girl in Figure 1 dance with the
  capybara in Figure 2.”
- LightX2V's pinned
  [Qwen-Image-Edit-2511
  example](https://github.com/ModelTC/LightX2V/blob/b96309e82899145aebd8ecf95c387894aba66b1e/examples/qwen_image/qwen_2511_fp8.py#L46-L64)
  uses “Replace the polka-dot shirt with a light blue shirt.” Its pinned
  [2511 Lightning
  configuration](https://github.com/ModelTC/LightX2V/blob/b96309e82899145aebd8ecf95c387894aba66b1e/configs/qwen_image/qwen_image_i2i_2511_distill_fp8.json)
  supplies a LightX2V-owned system template to the multimodal conditioner. That
  template asks it to inspect the input image and relate its features to the
  edit; it is a wrapper contract, not a hidden text report generated by the
  Qwen checkpoint.

Two apparent contradictions need precise interpretation:

1. FLUX.2 has no separate negative-prompt mechanism. An edit may still say
   “remove the sprinkles”, “without headphones”, or “keep everything else
   unchanged”, because removal and preservation can be relevant requested
   actions. Do not add a negative keyword list or mention unrelated things
   merely to forbid them.
2. FLUX.2 Klein's weights do not contain a built-in prompt upsampler. The
   official Hugging Face Space optionally wraps the model with a separate VLM.
   Our local route must therefore be sufficiently explicit, but it does not
   benefit from bloated prose.

## Required shape

A single-reference edit prompt answers, in normal language:

1. What visible transformation should happen?
2. What should the result look like?
3. Which small number of visual facts must remain unchanged for this edit to
   be correct?

Use one imperative instruction or one compact visual description. Put the
transformation and primary subject first. Add style, view, action, background,
or composition only when they affect correctness.

For a simple single-subject edit, one sentence is the default. Roughly 10–40
words is a useful operating range, not a quota. A longer prompt is justified
only by genuinely complex content or multiple reference roles.

## Grounding rules

- Every concrete noun and relationship must be visible in an input, requested
  by the user, or required in the output.
- Describe the desired visible result, not how the model should reason about
  fragments of the input.
- If view or action is ambiguous at low resolution, add the smallest sufficient
  set of short, confidently grounded facts, such as `rear view`, `facing left`,
  or `reclining`.
- Do not infer hidden anatomy, unseen clothing construction, or object
  attachment. The source image remains the visual authority.
- Do not enumerate every garment, accessory, color, and body part when the
  source image already supplies them.
- Do not promise pixel-perfect preservation from a semantic image editor.
  Preserve only the invariants needed for the paired-data task, then verify the
  output visually.
- With one input image, `this image`, `this sprite`, or the visible subject is
  usually the most natural wording. `image 1` or `Picture 1` is supported, but
  adds no information unless the runtime or surrounding instruction uses that
  label.
- With multiple input images, assign each numbered image one explicit role.
  This is where `image 1`, `image 2`, and so on become important.

Qwen's upstream rewriter permits reasonable inference when a user's request is
underspecified. The stricter visible-grounding rule above is repository policy
for paired corpus construction: invented details corrupt supervision even when
they make a standalone edit look plausible.

## Negative wording

For FLUX.2, never construct a negative-prompt list. For the repository's
Qwen-Image-Edit-2511 Lightning route, the established no-CFG execution also
uses an empty negative prompt.

An explicit edit action such as `remove the hat` is valid. A positive
preservation clause such as `keep the white background` is also valid. An
economical natural clause using `without` or `unchanged` can be valid when it
directly defines the requested edit. An unrelated prohibition is not.

In particular:

- Never add `no watermelon` to a prompt for an image that has nothing to do
  with a watermelon. It mentions an irrelevant concept and contributes no
  description of the desired image.
- Never append generic negative tags such as `no distortion, no extra limbs,
  no artifacts`.
- Never translate a semantic mistake into a growing list of forbidden nouns.
  Clarify it with the smallest sufficient set of grounded view or action facts;
  use seed selection or reject the candidate if the input remains ambiguous.

## Language that is forbidden

Reject a prompt containing model-facing pseudo-analysis or invented topology,
including phrases like:

- `and connected to the reclining body`
- `treat this region as part of the person`
- `recognize the separate object`
- `preserve topology`
- `do not interpret this shape as`

These phrases are not normal visual descriptions. They leak a speculative
diagnosis into the prompt, often introduce concepts that were not requested,
and produce brittle instructions no official example resembles.

Also reject:

- long inventories headed by `preserve exactly`;
- repeated `same`, `exact`, `unchanged`, or `without` clauses;
- quality incantations such as `masterpiece, best quality, 8K` when they do not
  describe the requested medium;
- prose explaining why the edit is difficult;
- character-specific facts copied into pipeline constants.

## FLUX.2 Klein

- Use one direct instruction. Prefer desired-output wording, while allowing a
  concise relevant removal or preservation clause.
- Put the transformation, subject, and critical view or action before
  secondary style detail.
- Describe style with visible traits rather than vague praise.
- The official image-aware rewriter's 50–80-word range is an upper pattern for
  involved edits, not a reason to inflate every prompt.
- Prompt following is sensitive to wording. Compare seeds under the exact same
  prompt before changing both prompt and sampling variables at once.
- If a per-image prompt is needed, add only the smallest sufficient set of
  disambiguating visual facts. Do not write a miniature scene graph.

## Qwen-Image-Edit-2511 through LightX2V

- Keep the external prompt as the user's direct edit request. LightX2V's
  wrapper template already asks the Qwen conditioner to inspect color, shape,
  texture, objects, and background.
- A clear prompt should not be expanded merely because a rewriter is
  available. Outside the character pipeline, this does not forbid running an
  established image-aware rewriter; its result must retain the original intent
  and remain direct rather than semantically inflating an already sufficient
  request. The character pipeline remains governed by
  [`docs/PLAN.md`](PLAN.md): no external VLM may author character descriptions
  into its generation prompt.
- Add minimal missing position, orientation, or style information only when it
  is visible and necessary.
- Use numbered image roles when they disambiguate actual inputs. LightX2V
  internally labels even a single 2511 image as `Picture 1`, so numbering is
  supported but optional for a one-image edit.
- Do not populate the empty negative prompt for the established 8-step,
  no-CFG route.
- The pinned LightX2V route resizes the condition image to an area of 147,456
  pixels (roughly 384×384 for a square input) and creates a separate VAE image.
  Its multimodal conditioning can guess a plausible interpretation, but it
  cannot recover or verify ground truth absent from an ambiguous 128×128
  sprite. A compact, grounded prompt may disambiguate those facts; the wrapper
  template cannot establish missing ground truth.

## Reverse-source prompts for the pix2pix corpus

The iRO reverse-source task is a single-reference whole-image style
conversion:

```text
pixel-art sprite -> smooth non-pixel anime illustration
```

The desired pair retains the visible subject, view, action, design, and broad
composition. The conversion changes the rendering medium. Cropping,
normalization, and final raster placement belong to the corpus pipeline, not
to an overconstrained prompt.

A suitable baseline has the same ordinary shape as the model-owner examples:

> Redraw this pixel-art sprite as a clean anime illustration with smooth
> linework and shading, keeping the same character, pose, view, and white
> background.

This is a baseline for review and controlled testing, not proof that every
low-resolution sprite is semantically unambiguous.

For an ambiguous sprite, add the smallest sufficient set of grounded
modifiers:

```text
Redraw this rear-view pixel-art character ...
Redraw this reclining pixel-art character ...
Redraw this left-facing pixel-art character ...
```

Do not explain how limbs or garments connect. If concise grounded modifiers and
multiple seeds still fail, reject that candidate or route it for human review.
More prose does not recover information absent from the pixels.

## Authoring and review workflow

Before a model run:

1. The prompt author reads this complete document.
2. The author inspects every input image the prompt refers to.
3. The author writes one direct instruction using only grounded visual facts.
4. A separate reviewer who has also read this document checks the prompt.
5. The exact prompt, input identity, model route, sampler settings, and seed
   set are recorded as provenance before generation.

The reviewer rejects the prompt if any answer below is `no`:

- Is it a normal instruction a human could naturally give an image editor?
- Is the requested transformation stated near the beginning?
- Is every mentioned object relevant and grounded?
- Does it avoid pseudo-analysis and invented spatial relationships?
- Does it avoid an unrelated negative list?
- Are any image numbers meaningful and consistent with the supplied inputs?
- Is every preservation clause necessary to judge the edit?
- Could the same prompt shape work for a completely different character?

Reading this document is part of prompt review. “Reviewed by a subagent” is not
valid provenance unless that subagent explicitly confirms it read this file.
